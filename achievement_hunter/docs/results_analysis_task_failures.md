## `oh_shiny`: primarily a representation and source-mapping failure

The PTD models the apple subgoal too abstractly. In the golden-apple PTD, `apple` appears as a resource vertex with no acquisition dependency in [craft_a_golden_apple_have_a_golden_apple_in_the_inventory.json](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/docs/ptd_jsons/craft_a_golden_apple_have_a_golden_apple_in_the_inventory.json:20). The fallback source resolver then treats unknown block resources literally: block sources are looked up from `canonical_block_source_by_target` in [mc_sources.js](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/src/pipeline/mc_sources.js:152), and if there is no special-case mapping the fallback returns the candidate id itself in [mc_sources.js](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/src/pipeline/mc_sources.js:268).

That abstraction turns into an invalid action at runtime. In a representative failure, the next task is an apple search sweep at [seed_-1427512363003067600/oh_shiny/runner_stdout.log](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/evaluation_harness/experiments/achievement_hunter_eval_v2_full/our_agent/seed_-1427512363003067600/oh_shiny/runner_stdout.log:24), and the search immediately fails with `Invalid block type: apple.` at [line 28](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/evaluation_harness/experiments/achievement_hunter_eval_v2_full/our_agent/seed_-1427512363003067600/oh_shiny/runner_stdout.log:28). The same run later enters repeated apple-search replanning and eventually times out at [line 793](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/evaluation_harness/experiments/achievement_hunter_eval_v2_full/our_agent/seed_-1427512363003067600/oh_shiny/runner_stdout.log:793). Across the 7 failing runs, I counted 113 invalid `apple` block searches.

The rest of the task usually succeeds. Across 7 of 8 runs, the agent still reaches `raw_gold` and then `gold_ingot`, which means the dominant failure is not gold acquisition and is hard to explain as a simple long-horizon timeout. The single successful run reinforces that point: the episode finishes successfully at [seed_-7169676182496905000/oh_shiny/episode_runtime.json](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/evaluation_harness/experiments/achievement_hunter_eval_v2_full/our_agent/seed_-7169676182496905000/oh_shiny/episode_runtime.json:10), and the agent goes straight to the golden-apple craft step at [seed_-7169676182496905000/oh_shiny/runner_stdout.log](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/evaluation_harness/experiments/achievement_hunter_eval_v2_full/our_agent/seed_-7169676182496905000/oh_shiny/runner_stdout.log:406) without any apple-search loop.

The most plausible explanation for that lone success is incidental apple pickup while gathering other resources, especially wood. That is an inference rather than a directly logged apple-drop event, but it matches both the PTD flaw and the runtime behavior: once an apple is already in inventory, the task becomes easy.

## `ice_bucket_challenge`: primarily a `water_bucket -> lava` execution bug

The obsidian PTD itself is reasonable. It requires `water_bucket + diamond_pickaxe + lava_source` in [obtain_a_block_of_obsidian_have_a_block_of_obsidian_in_the_inventory.json](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/docs/ptd_jsons/obtain_a_block_of_obsidian_have_a_block_of_obsidian_in_the_inventory.json:8), [line 14](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/docs/ptd_jsons/obtain_a_block_of_obsidian_have_a_block_of_obsidian_in_the_inventory.json:14), [line 26](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/docs/ptd_jsons/obtain_a_block_of_obsidian_have_a_block_of_obsidian_in_the_inventory.json:26), and [line 106](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/docs/ptd_jsons/obtain_a_block_of_obsidian_have_a_block_of_obsidian_in_the_inventory.json:106). The problem is downstream in execution and verification.

The core bug is in the `!useOn` verifier. `USEON_FILLED_BUCKET` maps `lava` to `lava_bucket` in [command_verifier.js](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/src/pipeline/command_verifier.js:636), and the verifier treats every bucket-like `!useOn(..., "lava")` as a bucket-filling event in [command_verifier.js](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/src/pipeline/command_verifier.js:623). That logic is correct for `!useOn("bucket", "lava")`, but wrong for `!useOn("water_bucket", "lava")`, where success should mean obsidian formation rather than a `lava_bucket` inventory delta.

The logs show that exact mismatch. In the representative failing run `seed_-1484597276503357200`, the obsidian subtask issues `!useOn("water_bucket", "lava")` at [runner_stdout.log](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/evaluation_harness/experiments/achievement_hunter_eval_v2_full/our_agent/seed_-1484597276503357200/ice_bucket_challenge/runner_stdout.log:593). The action later reports `Used water_bucket on lava.` at [line 669](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/evaluation_harness/experiments/achievement_hunter_eval_v2_full/our_agent/seed_-1484597276503357200/ice_bucket_challenge/runner_stdout.log:669), but that same attempt is immediately reclassified as `bucket_unfilled` at [line 666](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/evaluation_harness/experiments/achievement_hunter_eval_v2_full/our_agent/seed_-1484597276503357200/ice_bucket_challenge/runner_stdout.log:666). This pattern appeared in 3 of the 4 runs that actually reached the `water_bucket -> lava` step.

There are secondary contributors, but they look secondary rather than primary.

- Water filling is flaky in some seeds. In `seed_-1427512363003067600`, the run retries `!useOn("bucket", "water")` several times with `Could not fill bucket with water.` starting at [line 338](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/evaluation_harness/experiments/achievement_hunter_eval_v2_full/our_agent/seed_-1427512363003067600/ice_bucket_challenge/runner_stdout.log:338).
- Lava-edge interaction is unstable. In `seed_-1484597276503357200`, the bot dies during the lava step at [line 842](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/evaluation_harness/experiments/achievement_hunter_eval_v2_full/our_agent/seed_-1484597276503357200/ice_bucket_challenge/runner_stdout.log:842). Across the 8 runs, I found 2 lava-step deaths.
- Modes interfere near lava and obsidian. The self-preservation mode auto-uses water buckets around lava and fire in [ah_modes.js](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/src/agent/ah_modes.js:129), which is a plausible interference surface for these obsidian episodes. I also observed mode-interruption failures in 4 of the 8 runs.

The lone success is important because it shows the task can succeed once the broken bucket workflow is bypassed. In `seed_-4149976519821345000`, the run gives up on crafted obsidian and searches for natural obsidian at [runner_stdout.log](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/evaluation_harness/experiments/achievement_hunter_eval_v2_full/our_agent/seed_-4149976519821345000/ice_bucket_challenge/runner_stdout.log:1220). It then eventually mines obsidian successfully at [line 1373](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/evaluation_harness/experiments/achievement_hunter_eval_v2_full/our_agent/seed_-4149976519821345000/ice_bucket_challenge/runner_stdout.log:1373).

That escape hatch strongly suggests the low `1/8` success rate is not mainly a horizon problem. The core failure mode is that the intended `water_bucket -> lava` path is misverified.

## `the_lie`: horizon matters, but two model bugs dominate

`the_lie` does have a longer horizon than the other tasks. Its PTD combines egg, sugar, wheat, buckets, iron, and milk in [bake_a_cake_have_a_cake_in_the_inventory.json](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/docs/ptd_jsons/bake_a_cake_have_a_cake_in_the_inventory.json:14), [line 26](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/docs/ptd_jsons/bake_a_cake_have_a_cake_in_the_inventory.json:26), [line 32](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/docs/ptd_jsons/bake_a_cake_have_a_cake_in_the_inventory.json:32), and [line 110](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/docs/ptd_jsons/bake_a_cake_have_a_cake_in_the_inventory.json:110). But the logs and code indicate that the timeout is amplified by two concrete task-model problems.

The first problem is egg acquisition. Eggs are modeled as mob-acquired resources, and mob-acquired resources are always converted into `kill` tasks in [tasks.js](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/src/pipeline/structured_loop/tasks.js:104) and [tasks.js](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/src/pipeline/structured_loop/tasks.js:193). At runtime, that means the planner operationalizes `egg` as "kill chickens until an egg appears." In the representative run `seed_-1427512363003067600`, the agent attacks chickens starting at [runner_stdout.log](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/evaluation_harness/experiments/achievement_hunter_eval_v2_full/our_agent/seed_-1427512363003067600/the_lie/runner_stdout.log:266), then gets repeated `no_drop_for_chicken` verifier failures such as [line 286](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/evaluation_harness/experiments/achievement_hunter_eval_v2_full/our_agent/seed_-1427512363003067600/the_lie/runner_stdout.log:286). Across the corpus, 8 of 8 runs search for eggs early, and 7 of 8 runs attack chickens.

The second problem is that milk is never operationalized into a usable action. `mc_sources.js` correctly maps `milk_bucket` to `cow` in [mc_sources.js](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/src/pipeline/mc_sources.js:201), but `try_make_interact_task` only resolves acquisition dependencies for `water_source` and `lava_source` via [tasks.js](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/src/pipeline/structured_loop/tasks.js:219) and [tasks.js](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/src/pipeline/structured_loop/tasks.js:257). There is no equivalent route for `milk_bucket -> cow`. The empirical consequence is exactly what the code predicts: across all 8 `the_lie` runs, I found zero cow searches and zero `milk_bucket` mentions in the logs.

There is also a crop-execution issue that wastes additional time. Several runs repeatedly harvest immature wheat and get only seeds. In `seed_-1427512363003067600`, the wheat collection loop starts at [runner_stdout.log](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/evaluation_harness/experiments/achievement_hunter_eval_v2_full/our_agent/seed_-1427512363003067600/the_lie/runner_stdout.log:1441), where `!collectBlocks("wheat", 3)` is repeatedly reclassified because it only collected `wheat_seeds`. The recovery loop eventually diagnoses this and switches to hay-bale conversion at [line 1521](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/evaluation_harness/experiments/achievement_hunter_eval_v2_full/our_agent/seed_-1427512363003067600/the_lie/runner_stdout.log:1521), then crafts wheat successfully at [line 1541](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/evaluation_harness/experiments/achievement_hunter_eval_v2_full/our_agent/seed_-1427512363003067600/the_lie/runner_stdout.log:1541), but the task still times out because the milk path is still missing. A corpus-level scan found four `the_lie` runs with large `wheat_seeds` loops.

So the right conclusion is not "cake is too long-horizon, full stop." Horizon does matter, but the current planner spends a large fraction of the timeout budget on impossible egg acquisition behavior, a missing milk acquisition behavior, and low-yield crop collection. Those issues make the task look more horizon-limited than it really is.

## Additional observations

- The `oh_shiny` omission from the merged reporting files is itself an evaluation-harness bug or merge bug. It is separate from the gameplay failure, but it matters for thesis reporting because the raw manifests and merged summaries currently disagree.
- The `!useOn` verifier bug likely slipped through because the current verifier tests cover `bucket -> lava` and `bucket -> water` in [command_verifier_useOn.test.js](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/src/pipeline/__tests__/command_verifier_useOn.test.js:6) and [line 28](/C:/Users/Tom/Documents/Research/Thesis/embodied-intelligence-minecraft/achievement_hunter/src/pipeline/__tests__/command_verifier_useOn.test.js:28), but not the obsidian-critical `water_bucket -> lava` case.

## Bottom line

The three failures are qualitatively different.

- `oh_shiny` mostly fails because the planner cannot ground "apple" into a real source, so it emits invalid apple searches. This is a representation problem.
- `ice_bucket_challenge` mostly fails because the intended obsidian-creation interaction is misverified, and lava-edge safety behavior makes that brittle execution path even worse. This is primarily an execution and verification problem.
- `the_lie` fails partly because it is long-horizon, but mostly because the current task model turns eggs into chicken kills, never turns milk into cow-milking actions, and sometimes wastes time harvesting immature wheat. This is a task-model problem with a horizon overlay.
